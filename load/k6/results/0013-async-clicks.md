# 0013 재측정 — 클릭 집계 비동기화 뒤 처리 한계

plan: `docs/plans/0013-async-click-aggregation/plan.md`. 기준선: [`0012-baseline.md`](0012-baseline.md). 실행법: `load/k6/README.md` "한계 측정".
측정 창 두 번이었다. `spread`는 첫 창(2026-10-12 06:57~07:18 UTC), `hot`·`read`는 둘째 창(2026-10-12 23:17 ~ 10-13 00:06 UTC, 한국 10-13 오전)에 쟀다. 발생기는 같은 노트북이다.

## 결론

| 시나리오 | 0012 한계 | **0013 한계** | 0013 무릎 |
| --- | --- | --- | --- |
| `spread` 링크 100개 리다이렉트 | ≥1600 | **≥3200** | 없음 |
| `hot` 링크 1개 리다이렉트 | **400** (무릎 800) | **≥3200** | **없음** |
| `read` 조회만 | ≥1600 | **≥3200** | 없음 |

- **(a) 첫 병목이 사라졌다.**
  - `hot` 800 rps의 p95가 118.6ms에서 2.6ms로 내려갔다. 0012에서 무너졌던 1600은 2.2ms, 새로 더한 3200은 2.4ms였다.
  - 인기 링크 한 행에 리다이렉트마다 걸던 UPDATE가 태스크당 초당 한 번(`clicks + n`)으로 바뀌었다. 그래서 행 잠금 경합이 없어졌다.
  - 이제 리다이렉트는 조회(SELECT)만 하므로, 저부하 p95도 `read`와 같은 2ms대로 내려왔다(0012 `spread`·`hot`은 약 5ms).
- **(b) 클릭 수가 유실·중복 없이 맞았다.** 서버 쪽 불변식 `recorded − dropped = applied + unknown = DB 합계`가 세 실행 모두 정확히 성립했다(아래 정합성 표).
  중복 반영 배치 0, 발행·반영 실패 0, 버린 클릭 0.
- **(c) 다음 병목은 앱 CPU다.** 3200 rps까지 판정표의 어느 행도 걸리지 않았다. 다만 `spread` 3200에서 태스크 하나가 CPU 최대 97.5%에 닿았다(평균 72.6%).
  0.25 vCPU 태스크 2개로는 3200 rps 근처가 CPU 여유의 끝이다. 0014(EKS)의 HPA는 CPU로 늘리는 것이 맞다.

## 그 밖의 관찰

- **같은 코드 경로인데 측정 창마다 태스크 CPU가 크게 다르다.**
  - `read` 1600의 태스크 CPU가 0012(48.7%)의 거의 절반(26.3%)이다. 조회 경로는 0013에서 바뀌지 않았다.
  - `spread` 3200에서는 평균 72.6%·최대 97.5%로, 태스크 두 개 중 하나만 유독 높았다. 태스크가 2개라면 다른 하나는 약 48%다(2 × 72.6 − 97.5).
  - Fargate 태스크가 올라간 호스트 세대에 따라 CPU 성능이 다른 것으로 본다. 확정하지는 못했다. **CPU 비교는 같은 측정 창 안에서만 의미가 있다.** 0014 재측정은 세 시나리오를 한 창에서 잰다.
- **1600·3200에서 p99가 10~30ms로 오른다.** 풀 대기가 함께 늘고, `read`도 그렇다(쓰기 없음). `hot` 800 한 분에는 `in_use`가 25에 닿았고 p99가 71.5ms였다.
  p95는 2ms대 그대로다. 0.25 vCPU에서 고루틴 스케줄링이 밀려 연결을 오래 쥐는 것으로 추정한다. 앱 CPU 병목의 꼬리 증상이다.

## 0012와 측정 방법이 다른 점

- 단계에 3200 rps를 더했다(`MAX_RPS=3200`). k6 `preAllocatedVUs`를 100에서 200으로 올렸다. 열린 모델이라 서버 부하는 같다.
- `teardown`이 반영이 멈출 때까지 기다린 뒤 DB 합계를 찍는다(비동기 반영).
- 정합성은 서버 통계(`click queue` 로그: `recorded_clicks`·`dropped_clicks`·`applied_clicks`·`unknown_clicks`)로 판정한다. plan의 관측 절은 `unknown_codes`라고 적었지만 코드는 클릭 수인 `unknown_clicks`다(코드 검토 r1 #5).
- 측정 창 두 번. 첫 창의 `hot`은 200 rps 단계에서 사람이 중지해 버렸고(이동 때문), 둘째 창에서 `hot`·`read`를 다시 쟀다. 각 창은 인프라를 새로 만들었다.

## 0014로 넘길 것

- **다음 병목은 앱 CPU다.** `spread` 3200에서 태스크 하나가 97.5%였다. EKS에서는 HPA를 CPU 기준으로 두고, 파드 CPU 요청·한도를 0.25 vCPU에 묶어 둘지부터 정한다.
- **재측정은 세 시나리오를 한 창에서**, 같은 도구(`capacity.js` `MAX_RPS=3200`, `collect-metrics.sh`)로 한다. 이 문서와 0012가 비교 기준이다.
- **클릭 발행 실패 알람**(코드 검토 r1 #4)은 0015로 이월된 상태다.
