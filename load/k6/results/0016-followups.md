# 0016 — 0015 후속 정리(GOMAXPROCS 기본값·ArgoCD 알림·매 분 :00초 정지·요청 로그 표본화)

> 측정 창 2026-10-15(05:06~07:24 UTC, 켜기부터 끄기까지). plan: [`docs/plans/0016-observability-followups/plan.md`](../../docs/plans/0016-observability-followups/plan.md)
> `spread`를 3200 rps까지 세 번(r0 → r1 → r2), 실행마다 설정 하나만 바꿨다. 끝나고 고루틴 스냅숏용 짧은 실행(g1, 200 rps까지) 하나를 더 했다.

## 결론

- **매 분 :00초 정지는 서버·AWS 쪽이다. 발생기(맥·k6)가 아니다.** k6 시작을 정각 + 30초로 비킨 r0에서도 정지가 벽시계 :00초에 남았다.
- **정지는 앱 핸들러 안에서 기다린다.** 앱이 잰 처리 시간(로그 쓰기 제외)도 :00초 p99가 309~423ms다. CPU 여유가 큰 50 rps에도 있어 **DB(RDS) 응답 대기가 가장 유력**하다. 고루틴으로 직접 확인하지는 못했다(G-22·g1 — 아래).
- **요청 로그 표본화는 의도대로 동작한다.** 표본 줄 수가 기대와 0.2% 안에서 맞고, 3200 rps에서 Fluent Bit CPU −96%, 로그 양 −99%다. 앱 CPU도 7~21% 줄었다.
- **`GOMAXPROCS=1`은 CPU를 14~25% 줄인다.** 다만 로그를 전부 쓰면(r1) 정지 밖 꼬리 지연이 plan의 기준을 넘었다. 운영 조합(r2, 표본화 포함)은 기준 안이고 r0보다 낫다 → **기본값 1을 유지한다**(plan의 "넘으면 되돌림"과 다른 판단 — 아래 (a)). 런북 R-7(로그 전부 남기기)에 `GOMAXPROCS=2`를 함께 넣으라고 적었다.
- 운영 기본값(r2)의 3200 rps 요청당 CPU는 r0(0015 설정)의 약 2/3다(100 rps당 35 → 23m). HPA가 파드 6개 대신 5개로 버텼다.
- ArgoCD 알림 오탐 없음. 클릭 정합성 세 실행 모두 정수 일치.
- **새로 안 것 — Prometheus 분 단위 지표는 :00초 정지를 거의 못 본다.** 긁기가 :07·:22·:37·:52라 `increase(...[1m])`가 직접 세지 않는 틈(:52~:07)에 정지가 있다. 꼬리 지연은 ALB 접근 로그·앱 로그로 본다.

## 창 전 분석 (0012~0015 원자료, 인프라 없이)

도구: `load/k6/alb-latency.py`(ALB 접근 로그를 초 단위로, 클라이언트 IP를 찍지 않는다). 0015 일곱 실행(재측정 `spread`·`hot`·`read`, 1차 창 `e1`·`e3`·`e4`·`e1b`)에 돌렸다.
초는 도착 시각(`request_creation_time`), 시간은 대상 처리 시간(`target_processing_time`)이다. "정지"는 벽시계 :00~:02초(시작이 정각이라 k6 기준과 같다), "정지 밖"은 정지도 :30~:32초도 아닌 초다 — 30초 비킨 r0과 같은 초 집합으로 비교하려고 :30~:32를 모든 실행에서 뺀다.

### 도구 검증

- 분별 전체 p99가 0015 `-metrics.md`의 CloudWatch p99와 **88분 모두 10% 안**이다(그중 9분은 낮은 단계에서 1ms 해상도 때문에 1ms 차이로만 맞았다).

## 정지 판정 (c)

- **G(발생기)는 아니다.** r0은 k6 시작이 :30이었다. 정지는 모든 단계에서 벽시계 :00초에 있었고, k6 기준 :00초(벽시계 :30초)는 다른 초와 같았다.

  | r0 단계 | 벽시계 :00초 p99 / 50ms 초과 % | k6 기준 :00초 p99 / 50ms 초과 % |
  | --- | --- | --- |
  | 400 | 428 / 30.7 | 15 / 0.0 |
  | 800 | 794 / 27.6 | 28 / 0.2 |
  | 1600 | 242 / 21.8 | 30 / 0.2 |
  | 3200 | 354 / 30.7 | 48 / 1.0 |

- **핸들러 안에서 기다린다.** Logs Insights로 3200 유지 구간의 앱 `duration_ms`(핸들러 시작~끝, 로그 쓰기 전)를 앱 로그 `time`의 초로 나눴다.
  :00초 p99 r0 329·r1 309·r2 423ms(최대 418~521ms), 다른 초는 대부분 1~6ms다. :30·:45초의 약한 봉우리도 앱 시간에 있다(r2 :45초 p99 239ms).
- **CPU가 아니다.** 정지는 50 rps(파드 CPU 16~20m, 스로틀 0)에도 있다. 두 런타임(ECS·EKS)·모든 파드·두 AZ에 동시에 있다(창 전 분석).
  핸들러가 하는 일은 링크 조회 SELECT(RDS)와 클릭 기록(메모리)이고, `read`(클릭 없음)에도 정지가 있었다 → **RDS 응답이 가장 유력**하다. 직접 증거(고루틴이 DB 응답 대기에 몰림)는 없다.
- **고루틴 스냅숏을 얻지 못한 이유.** r0~r2: `goroutine-snap.sh`가 실행 권한 없이 커밋돼 백그라운드에서 조용히 실패했다(ops-gotchas G-22, 고침). g1(200까지, 스냅숏 5개): 그 분들의 정지가 작아(07:03:00 최대 140ms, 07:04:00 최대 29ms) +0.2초에 이미 끝나 처리 중 요청이 0이었다.
- **ALB 쪽 도착이 정각 첫 100ms에 약 2배다**(g1 파드당 19~20 대 10). 0015에도 있었다(3200 520 대 320). 정지 동안 처리가 밀려 ALB가 받은 시각이 몰린 것인지, ALB 자체의 주기인지는 이 자료로 못 가른다.

## (a) 판단 — `GOMAXPROCS=1` 유지

- plan은 r1(GOMAXPROCS 1, 로그 전부)의 정지 밖 p99가 r0 + max(2ms, 20%)를 넘으면 기본값을 `"2"`로 되돌리는 PR을 낸다고 정했다. **r1은 1600·3200에서 넘었다**(+3·+5ms).
- 그러나 운영에 나가는 조합은 r2(GOMAXPROCS 1, 로그 1/100)다. r2는 r0보다 정지 밖 p99가 1600 +2ms(기준 안)·3200 −2ms, p95 4.3 → 2.8ms, 스로틀 9.6 → 1.8%, 요청당 CPU −34%다.
- r1의 꼬리 증가는 ALB 시간에만 있고 앱 히스토그램 p99는 거의 같다(11.3 → 12ms) — 핸들러 밖, 즉 P 하나가 요청마다 로그를 쓰는 비용으로 본다. 표본화하면 사라진다(r2).
- 되돌리면 운영 조합이 재지 않은 (2, 표본화)가 되고 CPU·스로틀 이득을 잃는다. **그래서 기본값 1을 유지한다.** 로그를 전부 남기는 경우(런북 R-7)에만 같은 조건이 생기므로, R-7에 "높은 부하면 `GOMAXPROCS=2`도 함께 넣는다"를 적었다.
- 한계: 설정마다 한 번씩만 돌렸다. 3~5ms 차이는 같은 창의 흔들림일 수도 있다.

## ArgoCD (b)

- 세 실행에서 `LinkpulseArgoCDAppUnhealthy` pending·firing 0분. Application health는 HPA 확장 때 `Progressing`이 30초 표본 1~3개씩, 실행 직전 재기동 직후 `Degraded`가 한 번씩(30초 안) 보였다.
  재기동 직후 `Degraded`는 새 파드의 지표가 아직 없어 HPA가 `FailedGetResourceMetric`이 된 것으로 추정한다(gitops-engine `health_hpa.go`는 그것을 Degraded로 본다). 15분 지속 조건이라 울리지 않는다.
- **어느 리소스가 `Progressing`을 냈는지는 기록하지 못했다.** `record-pods.sh`가 읽는 Application `status.resources[].health`가 비어 있었다(`Deployment=-`). ArgoCD 3.0부터 리소스 health를 Application `/status`에 저장하지 않는 것이 기본이다(argo-cd v3.5.5 `docs/operator-manual/upgrading/2.14-3.0.md` "Health status in the Application CR", `controller.resource.health.persist`). 소스상으로는 Deployment(`AvailableReplicas < UpdatedReplicas`)다.

## Prometheus 분 단위 지표의 틈 — :00초 정지를 못 본다

- 긁기 간격 15초, 이번 창의 앱 파드 긁기 시각은 :07·:22·:37·:52와 :13·:28·:43·:58이었다.
- 수집 표는 분 끝 t+60에 `increase(...[1m])`·`rate(...[1m])`를 묻는다. 창 (t, t+60]의 첫 긁기와 끝 긁기 사이만 직접 세고, 나머지 약 15초는 외삽으로 메운다.
  그 틈이 :52~:07(또는 :58~:13)이라 **매 분 :00초 정지가 어느 창에서도 직접 세어지지 않는다.**
- 그래서 Prometheus 절의 앱 p99·"100ms 초과 %"·"늘 남는 요청"이 정지를 거의 놓친다(3200 앱 p99 8~12ms, 같은 때 ALB :00초 p99 320~354ms). 0015의 "앱 p95/p99 4.8/5"도 같은 이유다.
- 정지·꼬리는 ALB 접근 로그와 앱 로그(초 단위)로 본다. 지표는 정지 밖의 정상 상태를 보는 데 쓴다.
