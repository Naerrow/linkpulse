한계 기준은 0012와 같다. 서버 쪽 p95(ALB `TargetResponseTime`)가 100ms 미만, 5xx 1% 미만, 발생기가 정상이면 그 단계를 통과로 본다.

- **(a) 관측성이 들어왔다.** Prometheus 대상 29개가 모두 `up`, linkpulse 규칙 그룹 4개가 `ok`, 공개 `/metrics`는 404다. 시험 알림이 규칙 → Alertmanager → SNS → Chatbot → **Slack에 발화·해소 모두 도착했다**(발화 약 30초 뒤).
- **(b) 클릭 정합성을 로그 대신 카운터로 정수 판정했다.** 실험 4회와 재측정 3회 **모두 `recorded − dropped = applied + unknown = DB 합계`가 정확히 맞았다**(리셋 0, 사라진 파드 0). 0014에서 로그 유실로 판정할 수 없었던 `hot` 6400도 맞았다.
- **(c) 로그 유실이 사라졌다.** Fluent Bit를 파일 시스템 버퍼·tail DB·`Rotate_Wait 30`으로 바꾼 뒤, 6400 포함 모든 유지 분에서 파드마다 주기 줄 6개가 다 남았다(의심 칸 0).
- **(f) ALB 502가 0이 됐다**(0014: 세 실행 12건). 서버 keep-alive를 60초 → 75초로 늘린 것(ALB 유휴 타임아웃 60초보다 길게)의 효과로 본다. 남은 실패는 클라이언트 타임아웃 18건이고, ALB 로그에 없으므로 서버 쪽이 아니다.
- **(e) "EKS 요청당 CPU가 ECS의 2~4배"의 원인은 다 가리지 못했다.** EKS 쪽 측정은 맞다(세 출처 일치). 로그는 원인이 아니다. `GOMAXPROCS=1`이 10~15%를 줄인다. 그 밖은 가리지 못했다 — 아래 "요청당 CPU 실험".
- **(g) P5 종결.** `full-apply-prod.sh` 한 번으로 처음부터 재현된다(2차 창에서 오류 없이). 1차 창에서는 두 오류(G-19 차트 저장소 타임아웃, G-20 metrics-server 애드온의 깨진 OpenAPI)를 만나 고쳤다. 6400의 벽은 0014와 같다 — **파드 CPU 한도(250m) × HPA 최대 6**, 그리고 DB 연결 풀(66)이 함께 찬다.

- 남은 큰 몫은 **요청마다 고정으로 드는 일**이다: 리다이렉트마다 하는 DB 조회(TLS 포함)와 네트워크 시스템 호출. 0014가 본 "시나리오와 무관한 고정 비용"과 맞는다.
- 다음 확인은 ②(노드 세대 — 예: Graviton3 노드 하나에서 같은 실험)다. ①의 ECS 쪽은 다시 잴 수 없으므로, 파드 크기·HPA는 **EKS에서 잰 값(100 rps당 약 35~40m)을 그대로 기준**으로 정하는 것이 맞다.

## 그 밖의 관찰

- **3200 단계 p99가 0014의 2~6배다. 원인은 가리지 못했다.**
  - 3200 단계 평균 파드 CPU는 0014와 비슷하다(77~78% 대 72~79%). p95도 같다.
  - 파드별 CFS 스로틀이 3200에서 3.9~14.8%다(스로틀은 0014에 없던 지표다). 평균 77%여도 순간 몰리면 250m 한도에 걸려 그 주기(100ms) 안에서 멈춘다 — p99 꼬리의 후보다.
  - 0014에서 바뀐 것: 노드 3대(파드가 노드당 2개씩), 모니터링 스택, Fluent Bit 파일 버퍼(3200에서 노드 디스크 바쁨 20~38%, 800에서 4~17%), 지표 계측, keep-alive 75초.
  - 노드 CPU는 3200에서 42~44%(6400에서 53~55%)라 노드 자체는 여유가 있었다.
  - 다음 측정에서 파드별 스로틀과 p99를 분 단위로 맞춰 본다.
- **Fluent Bit 비용이 크다.** 3200 rps에서 Fluent Bit가 노드 3대 합 **719m**를 썼다(800에서 232m). 같은 때 앱 파드 6개 합은 약 1,166m — 요청마다 쓰는 JSON 한 줄 접근 로그의 처리 비용이 앱 CPU의 약 60%다. 파드 CPU에는 잡히지 않는 노드 비용이다. 접근 로그 샘플링(0014 이월 3)이 비용 면에서도 근거가 생겼다.
- **6400에서 차는 것**: 파드 6개 모두 CPU 한도(cAdvisor 237~246m, 스로틀 88~92%)와 DB 연결 66(풀 11 × 6)이 함께 찬다. 풀 대기가 2분에 35~41만 건이다. RDS CPU는 45~52%로 여유가 있다. 앱 쪽 p95는 23~34ms인데 ALB p95는 61~66ms다 — 그 차이는 스로틀된 파드에서 요청을 받기까지의 대기다.
- **SQS 가장 오래된 메시지 나이**: `spread` 6400에서 최고 41초(0014: 69초). `hot`·`read`는 0초.
- **앱 히스토그램의 첫 경계가 5ms라** 앱 쪽 p95/p99는 3200까지 늘 4.8/5ms(보간)로 나온다. 5ms 아래는 구분하지 못한다. SLO 경계(100ms)에는 충분하다.
- **집 회선의 연결 멈춤**: 1차 창에서 세 번(G-19 차트 저장소, G-20 진단 중 EKS API, G-21 k6 setup) 같은 모양이었다. k6 setup은 응답이 없을 때 세 번까지 다시 보내게 고쳤다. 2차 창에서는 재시도가 한 번도 일어나지 않았다.

## 0014와 측정 방법이 다른 점

- 정합성을 Prometheus 카운터로 정수 판정한다(로그 합계 표는 비교용으로 남겼다). 평가 시각은 teardown 줄 + 30초다.
- 수집 표에 Prometheus 절이 붙었다: 앱 rps·지연, 파드 CPU 세 출처, CFS 스로틀, 연결당 요청, 실제 GOMAXPROCS, 파드·분당 주기 로그 줄 수.
- ALB 접근 로그로 실패 요청을 분류했다(`load/k6/alb-errors.py`, 클라이언트 IP를 찍지 않는다).
- 노드가 3대다. 노드 CPU·디스크(node-exporter)를 볼 수 있다.

## 0016으로 넘길 것

1. **`GOMAXPROCS=1`을 기본으로.** 250m 한도에서 Go가 2로 잡는다. 1로 두면 CPU 10~15%가 줄고 지연은 나빠지지 않았다. 차트 값으로 넣고(사이트 무관) 재측정으로 확인한다.
2. **`LinkpulseArgoCDAppUnhealthy`에서 `Progressing`을 뺀다**(또는 별도 조건으로). HPA 확장 중 오탐 후보다. promtool 테스트에 "Progressing 6분은 울리지 않는다"를 더한다.
3. **3200 p99 상승 원인**: 파드별 스로틀과 p99를 분 단위로 맞춰 본다. 스로틀이 원인이면 CPU 한도를 요청보다 높게(버스트 허용) 두는 것을 검토한다.
4. **접근 로그 샘플링** — Fluent Bit가 3200 rps에서 719m(앱의 약 60%)를 쓴다. 로그 양·CloudWatch 비용도 같이 준다.
5. **요청당 CPU 남은 후보 ② 노드 세대.** Graviton3 노드 하나에서 같은 E1을 건다. ECS 쪽 지표는 다시 잴 수 없으므로 판단은 EKS 값으로 한다.
6. **6400의 벽**(0014 이월): HPA 최대 6 × 250m와 DB 연결 66. 1·3이 끝난 뒤 `maxReplicas`·풀·PgBouncer를 정한다.
7. **외부 dead man's switch**(Watchdog을 클러스터 밖에서 받기)는 ADR 0008대로 P7로 둔다.
