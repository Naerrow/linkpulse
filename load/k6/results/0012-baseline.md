# 0012 기준선 — ECS 구성의 처리 한계와 첫 병목

측정일 2026-10-12(UTC 00:36~01:42). plan: `docs/plans/0012-capacity-baseline/plan.md`. 실행법: `load/k6/README.md` "한계 측정".
0013(클릭 집계 비동기화)·0014(EKS) 뒤 재측정은 이 표와 비교한다.

## 결론

| 시나리오 | 한계(기준을 모두 만족한 마지막 단계) | 무릎 |
| --- | --- | --- |
| `spread` 링크 100개 리다이렉트 | **≥1600 rps** | 없음 |
| `hot` 링크 1개 리다이렉트 | **400 rps** | **800 rps**(p95 4.8 → 118.6ms) |
| `read` 링크 100개 조회(쓰기 없음) | **≥1600 rps** | 없음 |

- 기준: 서버 쪽 p95(ALB `TargetResponseTime`) < 100ms, 5xx < 1%, 발생기 정상.
- **첫 병목 = 인기 링크 한 행의 클릭 UPDATE 행 잠금 경합**(판정표 4번). 같은 800 rps에서 `spread`는 p95 5.5ms, `hot`은 118.6ms였다.
  이때 태스크 CPU 31%, RDS CPU 27~30%로 둘 다 여유가 있었다. 연결 풀이 25개 다 찬 것은 `hot`에서만 크게 나타났다 — 잠금을 기다리는 쿼리가 연결을 붙잡은 증상이다.
- **0013의 범위는 plan대로 확정한다.** 클릭 집계를 리다이렉트 경로에서 떼어 내면(큐 + 비동기 반영) 이 병목이 사라져야 한다. 재측정의 첫 확인 대상은 `hot`이다.

## 구성 사양

- 앱: main `9bdb51d`(PR #25). ECS Fargate 태스크 **2개 × 0.25 vCPU·512MB, ARM64**. 연결 풀 태스크당 25(최대 50).
- DB: RDS PostgreSQL 16, **db.t4g.micro**(Unlimited), 스토리지 20GB. 측정 전 빈 DB.
- 리전 ap-northeast-2. 부하 발생기는 서울 가정 회선의 노트북 한 대(macOS, 11코어), k6 v2.3.0.
- 측정 IP만 레이트리밋 예외(`RATE_LIMIT_EXEMPT_IPS`). **측정 IP는 리미터(전역 뮤텍스·버킷 조회)를 통째로 건너뛰므로 리미터 비용은 이 숫자에 빠져 있다.**
  요청 비용(DB 왕복·JSON 로그)에 비하면 무시할 수준이고, 0013·0014도 같은 방식으로 잰다(코드 검토 r1 #2).
- 단계: 50 → 100 → 200 → 400 → 800 → 1600 rps, 단계마다 30초 램프 + 2분 30초 유지. **단계 값 = 유지 구간의 온전한 2분**(CloudWatch 1분 지표 2개).

열 설명: p95·p99는 서버 쪽(ALB), 태스크 CPU는 ECS 서비스 평균/최대, 풀 대기는 2분 동안 기다린 건수/합계 ms, `in_use`는 10초 샘플의 최대.

## 클릭 정합성

| 시나리오 | `redirects_302` | DB 클릭 합계 | 서버 `"클릭 집계 실패"` |
| --- | --- | --- | --- |
| spread | 542,704 | 542,704 | 0 |
| hot | 357,806 | 357,857 | **260** |
| read | (조회만) | 0 | 0 |

- `hot`은 abort로 끝나 진행 중 요청 500개가 끊겼다. 그래서 DB 합계가 302 수보다 51 크다. plan 규칙("302 > DB일 때만 유실")으로는 유실을 가리지 못한다.
- 서버 쪽 실패 260건은 **모두 abort가 일어난 01:16 한 분에 몰려 있다.** 풀이 꽉 찬 800 rps 구간(2분)에는 0건이었다.
  가장 그럴듯한 원인은 k6가 연결을 끊으면서 요청 context가 취소돼 UPDATE가 취소된 것이다(`IncrementClicks`가 요청 context를 쓴다).
  오류 문구를 수집하지 않아 확정하지 못했다. 어느 쪽이든 **클릭 집계가 요청 수명에 묶여 있어 클라이언트가 끊기면 클릭이 사라진다**는 점은 0013이 함께 푼다.

## 그 밖의 관찰

- `spread` 1600에서 `dropped` 144건이 나왔지만 서버 지연은 오르지 않았다(p95 6.2ms). 판정 규칙대로 서버 포화가 아니라 k6의 VU 확보 지연으로 본다. `read` 1600의 31건도 같다.
- `spread`·`hot` 200과 `spread` 800·1600에서 풀 대기가 순간적으로 생겼다(10초 샘플의 `in_use` 최대는 1~5). 짧은 순간에 몰렸다가 풀린 것이고 p95에는 드러나지 않았다.
  같은 분의 p99가 튀었다(`spread` 200 17.9ms, `hot` 200 25.1ms). 첫 병목이 아니라 관찰로 남긴다.
- `read` 1600 램프 구간에서 클라이언트 쪽 요청 타임아웃 3건(status 0). ALB에는 5xx가 없어 회선·발생기 쪽으로 본다.
- 선형으로 늘리면 `spread`의 태스크 CPU는 약 2,600 rps에서 90%에 닿는다. 0013 뒤에는 **앱 CPU(0.25 vCPU × 2)가 다음 병목 후보**다.
  0013 재측정은 단계를 3200 rps까지 늘려야 `spread`·`read`의 한계가 보인다.

## 측정 중 고친 것

- `collect-metrics.sh`가 CloudWatch 열을 모두 비웠다. CloudWatch API가 CBOR 프로토콜이라 AWS CLI가 시각을 **로컬 시간대(`+09:00`)**로 준다. 스크립트가 UTC만 가정해 9시간 어긋났다.
  → 오프셋을 반영하도록 고쳤다. 원본 응답(`*-cw.json`)으로 원인을 확인했다.
- 풀 대기 열이 비었다. Logs Insights에서 `sum(wait_count) as wait_count`처럼 **별칭을 원래 필드 이름과 같게 두면 결과에서 그 열이 빠진다.** → 별칭을 `waits`·`waited_ms`로 바꿨다.
- 수집 스크립트가 원본 응답을 CSV 옆에 남기게 했다. destroy 뒤에도 표를 다시 만들 수 있다.
