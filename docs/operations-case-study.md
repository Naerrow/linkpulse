# 운영 사례 — 비밀번호 회전 이후의 DB 연결 실패

[프로젝트로 돌아가기](../README.md) · [원본 회고(초안)](postmortems/2026-09-06-rds-rotation-outage.md)

## 문제

RDS 비밀번호가 회전된 뒤 기존 애플리케이션이 기동 시 받은 자격증명을 계속 사용했습니다. DB를 사용하는 URL 생성·리다이렉트는 실패했지만, 프로세스 생존만 검사하는 `/healthz`는 정상 응답을 유지할 수 있었습니다.

## 탐지 개선

외부 점검을 `/healthz`에서 DB 연결 상태를 반영하는 `/readyz`로 바꿨습니다. Route53 헬스체크의 별도 지표를 사용해 실사용 트래픽이 없는 시간에도 장애를 탐지하도록 했습니다. 다만 DB의 짧은 중단도 canary 요청에 의한 5xx를 만들 수 있으므로 알람 민감도와 RDS 유지보수 창을 함께 해석해야 합니다.

근거: [ADR 0004](adr/0004-notraffic-canary.md), [헬스체크 구현](../app/internal/httpapi/health.go).

## 원본 회고에 기록된 타임라인

| 단계 | 기록 |
| --- | --- |
| 비밀번호 회전 | 2026-09-06 19:09 KST |
| 첫 ALB 알람 | 회전 후 5분 37초 |
| 수동 재배포 시작 | 2026-09-07 08:14:12 KST |
| canary OK | 2026-09-07 08:19 KST |
| 전체 장애 시간 | 13시간 10분 |
| 작업 시작 이후 복구 | 약 5분 |

위 값은 이번 작업의 실측이 아니라 **회고 기록의 인용**입니다. 원문은 초안 상태이며 근거 로그는 저장소 밖의 로컬 보관 자료라고 명시되어 있습니다. 전체 장애 시간을 복구 작업 시간과 혼동하거나, 자동 복구 성과로 제시하지 않습니다.

## 복구와 검증

회고에는 ECS 강제 재배포로 새 태스크가 현재 비밀번호를 받게 하고, `/readyz` 200과 실제 링크 왕복 302를 확인한 과정이 기록되어 있습니다. 상세 실행 순서와 진단 분기는 [비밀번호 회전 복구 런북](runbooks/secret-rotation-bridge.md) 및 [알람 대응 런북](runbooks/alarm-response.md)에 있습니다.

## 배운 점과 현재 상태

알림이 휴대전화에 도달해도 사람이 즉시 대응하지 않으면 복구는 시작되지 않습니다. 탐지 시간과 대응 시작까지의 지연을 별도로 보아야 합니다.

| 개선 항목 | 확인 상태 |
| --- | --- |
| DB readiness 기반 외부 점검 | 애플리케이션·Terraform·ADR에 반영 |
| 회전 이벤트 후 ECS 자동 재배포 | [Terraform](../infra/prod/rotation-redeploy.tf), [Lambda와 테스트](../infra/prod/lambda/rotation_redeploy/) 존재 |
| 자동 재배포의 라이브 적용·드릴 | 이번 문서 확인에서 완료를 확정하지 않음 |
| 앱 내부 자격증명 갱신 | [계획 0009](plans/0009-p4d2-rotation-resilience/plan.md)의 Step 2. 목표 시간을 실측으로 사용하지 않음 |
| 백업 기반 DB 복원 검증 | [ADR 0005](adr/0005-backup-restore-dr.md)의 범위에 따름. 서비스 전체 RTO와 다름 |

계획, 코드 존재, 라이브 적용, 드릴 결과를 각각 확인해야 재발 방지 완료라고 평가할 수 있습니다.
