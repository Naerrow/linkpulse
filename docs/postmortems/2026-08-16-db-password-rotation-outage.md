# 회고 — 2026-08-16 RDS 마스터 비밀번호 자동 로테이션으로 인한 전면 500 (66시간 미인지)

- 날짜(발생): 2026-08-16 22:13경 KST / 복구: 2026-08-19 16:44 KST
- 작성자: Naerrow / 검토자: —
- 심각도: SEV-1 (전 요청 500, 서비스 기능 전면 불능)
- 상태: 확정
- 관련: PR #14(500 원인 로깅), plan 0008(탐지, approved) · 0009(로테이션 근본 대응, 미작성) · 0010(탐지 드릴)
- 증거: `docs/postmortems/evidence/db-password-rotation-2026-08-19/`

## 1. 한 줄 요약

RDS가 관리하는 마스터 비밀번호가 **7일 주기 자동 로테이션**으로 갱신됐는데, 앱은 그 비밀번호를 **컨테이너 기동 시 1회만** 주입받는 구조라 커넥션 풀이 교체되는 5분 뒤부터 모든 DB 연결이 `SQLSTATE 28P01`(인증 실패)로 떨어졌다. **알람은 정상 작동해 2시간 6분 만에 울렸지만**, 절대 건수 임계(5건/5분)가 봇 스캔 트래픽 변동에 따라 **ALARM↔OK를 53회 왕복**하면서 "봇 소음"으로 읽혔고, 500 응답 경로에 원인 로그가 없어 로그만으로는 "없는 링크"와 "DB 장애"를 구분할 수 없었다. 그 결과 **인지까지 66시간**이 걸렸다. 복구는 `force-new-deployment` 한 번(30분).

## 2. 영향

- **기간**: 2026-08-16 22:13경 → 2026-08-19 16:44:19 (**2일 18시간 31분**)
- **사용자 영향**: 단축 링크 리다이렉트·생성·조회 **전 기능 불능**(모든 요청 500).
  다만 그 기간 트래픽의 **대부분은 Route53 헬스체크(인공)** 였고 나머지는 봇 스캔(`/*.php`, `/.env` 등)이었다.
  500 샘플 200건의 고유 경로 195개가 전부 스캐너 패턴 — **실사용자 피해는 제한적이었을 가능성이 높다.**
  단 이는 **운이었지 시스템이 막아준 것이 아니다**(실사용 클릭이 있었다면 동일하게 500).
- **데이터 영향**: 없음. RDS 인스턴스는 `available` 상태를 유지했고 스키마·데이터는 무손상.
  실패는 전부 **연결 인증 단계**에서 발생해 쓰기 자체가 도달하지 않았다.

## 4. 감지 — 무엇이 알려줬고, 무엇이 침묵했나

**발화한 알람**
- `alb-target-5xx` — 정상 작동. 다만 아래 이유로 심각도를 전달하지 못했다.

**침묵한 알람 (울었어야 했다)**
- `canary_down` (P4(c) 무트래픽 방어선) — **66시간 내내 초록불.**
  Route53 헬스체크가 `/healthz`를 프로빙하는데, 이 엔드포인트는 liveness라 **DB를 조회하지 않는다.**
- `alb-unhealthy-hosts` / `alb-elb-5xx` — 같은 이유로 침묵. ALB 타깃그룹 헬스체크도 `/healthz`라
  타깃은 계속 healthy였고, ALB가 자체 5xx를 만들 일이 없었다.
- **DB 상태를 보는 유일한 엔드포인트 `/readyz`는 아무도 호출하지 않고 있었다.**

**runbook이 막힌 지점**
- `docs/runbooks/alarm-response.md:17`(§0-2 초동 확인)이 `curl .../healthz`만 지시한다 →
  이 장애에서는 **200이 나온다** → "영향 없음/미미"로 분류된다.
- 같은 파일 `:193`(§13)은 *"`/healthz`가 200이면 오탐 의심"* 이라고 명시한다 →
  실장애를 오탐으로 기각하도록 유도한다.
- 즉 **런북을 정확히 따를수록 장애를 놓치게 되어 있었다.**

## 5. 원인 분석

### 5-1. 직접 원인

`manage_master_user_password = true`(`infra/prod/rds.tf:42`)로 RDS가 마스터 비밀번호를 관리하며,
로테이션 주기는 기본값 **7일**(`AutomaticallyAfterDays: 7`)이다.
앱은 이 값을 ECS `secrets`로 **컨테이너 기동 시 1회** 주입받는다(`infra/prod/ecs.tf:52`).
→ 로테이션 후 프로세스가 들고 있는 비밀번호는 즉시 무효가 된다.

기존 커넥션은 Postgres가 비밀번호 변경으로 세션을 끊지 않으므로 잠시 살아 있지만,
풀 수명 `ConnMaxLifetime = 5분`(`app/internal/db/db.go:29`)이 지나면 전부 교체되고,
새 연결은 전부 `28P01`로 거절된다. **로테이션 5분 뒤 전면 장애**가 되는 구조다.

### 5-2. 왜 66시간을 놓쳤나 (세 겹의 실패)

**① 알람이 심각도를 전달하지 못했다 — 절대 건수 임계의 함정**

`alb-target-5xx`는 `HTTPCode_Target_5XX_Count >= 5 / 5분` 기준이다(`monitoring.tf:57-59`).
성공률이 0%인데도 봇 스캔 트래픽이 간헐적이라 5분 버킷마다 5건을 넘겼다 말았다 했고,
그 결과 **ALARM↔OK를 53회 왕복(상태 전환 106회)** 했다. `ok_actions`도 SNS에 걸려 있어
**Slack 알림이 66시간 동안 106건** 갔다. 지속 장애가 간헐 소음처럼 보였다.

**② 로그에 원인이 없었다**

`create`/`redirect`/`stats` 핸들러가 저장소 오류를 그대로 버리고 500만 반환했다.
그 결과 **66시간 동안 앱 에러 로그가 0건**이었다(`03-app-non-info-logs.txt`의 유일한 1건은
08-19 진단 중 `curl /readyz`로 생성된 것). 로그에는 `{"level":"INFO","msg":"http request","status":500}`
한 줄만 남아, "없는 링크에 대한 404성 500"인지 "DB 장애"인지 구분할 방법이 없었다.

**③ 감시 지표가 장애 상황에서 의미를 잃었다**

`/healthz`(liveness)만 감시하고 있었으므로 DB가 죽어도 모든 헬스 신호가 초록불이었다.
더 나쁜 것은 그 헬스체크가 **분모를 채워 5xx 비율을 희석시켰다**는 점이다:

```
총 요청       132,382건   (시간당 약 1,976건, 66시간 내내 거의 일정)
5xx            4,735건   →  3.58%
```

시간당 1,976건이라는 평탄한 수치는 **30초 주기 Route53 헬스체크**로 설명된다
(글로벌 체커 약 16지점 × 시간당 120회 ≈ 1,900건). 즉 분모의 대부분이 인공 트래픽이다.
정확한 헬스체크 건수는 별도 계측이 없어 위 값은 **추정**이며, 확정된 실측은 5xx 비율 3.58% 쪽이다.

**P4(c)에서 확인한 것과 같은 계열의 결함이다.** 그때는 `HealthyHostCount`가 대상 장애에서
지표 자체가 소멸(missing)해 알람이 무발화했고(ADR 0004 §A-5), 이번엔 `/healthz` 감시가
DB 장애에서 초록불을 유지하며 동시에 5xx 비율까지 희석시켰다.
→ **감시 지표는 정작 감시 대상이 고장 났을 때 의미를 잃을 수 있다.**

### 5-3. 왜 이 구조가 만들어졌나 (절차 수준)

`/healthz`(liveness)와 `/readyz`(readiness)를 분리한 설계 자체는 옳다.
문제는 **분리해 놓고 `/readyz`를 아무도 보지 않았다**는 것이다.
ALB 타깃그룹·Route53 canary 모두 `/healthz`를 골랐고, 그 선택은 각각 타당한 이유가 있었다
(LB 헬스체크를 readiness로 걸면 DB 블립에 전 타깃이 드레이닝된다).
**"어느 쪽도 readiness를 감시하지 않는다"는 공백은 두 결정 사이에서 생겼고, 아무도 소유하지 않았다.**

## 6. 잘 된 것 / 아쉬운 것 / 운이 좋았던 것

**잘 된 것**
- 진단이 빨랐다. `curl /readyz` **한 번**으로 DB 도달 실패를 확정했고, 앱이 남긴 `28P01` 원문으로
  네트워크·SG·인스턴스 상태를 전부 배제할 수 있었다(TCP·TLS·SASL 협상까지 진행됐다는 사실이
  "인증만 실패"를 증명한다). 인지 후 복구까지 34분.
- 증거를 먼저 확보하고 복구했다. `evidence/` 스크립트 한 번으로 알람 이력·로그·메트릭·원인 물증을
  파일로 남겨, 재배포로 상태가 바뀐 뒤에도 회고가 가능했다.
- 상식적 처방을 데이터로 검증했다(아래 액션 #7 참고).

**아쉬운 것**
- 알람 106건을 받고도 3일간 열어보지 않았다. 알람 피로는 임계 설계의 산물이지 개인의 부주의가 아니다.
- 500 경로에 원인 로깅이 없다는 것은 **코드를 쓸 때 알 수 있었던 결함**이다. 관측성(P3)을 했다면서
  가장 흔한 실패 응답의 원인을 버리고 있었다.

**운이 좋았던 것**
- 실사용 트래픽이 사실상 없어서 실제 피해가 제한적이었다. **다음엔 운에 맡기지 않으려면**
  탐지(0008)와 자동 회복(0009)이 필요하다.

## 8. 배운 것 (일반화)

1. **"알람이 없었다"와 "알람이 전달되지 않았다"는 다른 문제다.**
   이번 건은 후자였고, 처방도 다르다(알람 추가가 아니라 임계 설계·신호 선택).
2. **저트래픽 서비스에서 절대 건수 임계는 심각도를 반영하지 못한다.**
   성공률 0%인데 알람이 OK로 내려갈 수 있다.
3. **감시 지표는 감시 대상이 고장 났을 때 의미를 잃을 수 있다.**
   `HealthyHostCount` 소멸(P4(c))과 `/healthz` 초록불(이번)이 같은 패턴이다.
   *"이 지표는 내가 잡으려는 장애가 났을 때도 살아 있는가"* 를 설계 시점에 물어야 한다.
4. **인공 트래픽(헬스체크·canary)은 비율 기반 지표를 오염시킨다.**
   비율 알람을 설계할 때 분모에 무엇이 들어가는지 확인해야 한다.
5. **원인을 클라이언트에 숨기는 응답(500)일수록 로그에는 반드시 남겨야 한다.**
   숨긴 정보가 어디에도 없으면 사후 추적이 불가능해진다.
